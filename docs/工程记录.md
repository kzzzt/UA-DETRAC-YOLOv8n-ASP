## 一、项目意图

### 1.1 一句话目标

在 **YOLOv8n** 基线上做三项轻量改进，构建 **YOLOv8n-ASP**
（**A**ttention + **S**mall-object P2 + **E**IOU），在 **UA-DETRAC** 交通监控数据集上
提升**复杂天气（雨/雾/夜间）**与**远距离小目标车辆**的检测能力，且不显著增加计算开销。

### 1.2 三个改进点

| 模块 | 选型 | 解决的痛点 | 论文定位 |
|------|------|-----------|----------|
| ① 注意力增强 | **SimAM**（无参、3D 能量函数注意力） | 雨雾、夜间灯光、复杂背景干扰 | 主创新（零额外参数） |
| ② 小目标检测 | **新增 P2 检测层**（4 倍下采样，160×160@640） | 远处小尺寸车辆 | 主创新（增益最大） |
| ③ 损失函数 | **EIOU** 替换 CIoU | 加速收敛、提升定位精度 | 辅助优化 |

**为什么选 SimAM 而不是 CBAM/GAM**：基线是 nano 级模型，"轻量"是核心叙事；
CBAM/GAM 会引入额外参数，而 SimAM 无参却有效，与参考文献《YOLOv8-SimAM》结论一致。

### 1.3 数据集

| 项目 | 说明 |
|------|------|
| 名称 | UA-DETRAC（官方训练集 60 序列） |
| 分辨率 | 960 × 540 |
| 类别 | car(0) / bus(1) / van(2)，忽略 others |
| 官方天气标注 | XML 内 `<sequence_attribute sence_weather="...">`，取值 sunny/cloudy/night/rainy |
| 训练序列天气分布 | sunny 15 / cloudy 19 / night 16 / rainy 10 |

### 1.4 论文核心叙事（基于实测结果调整后）

1. **P2 是最稳的增益**：整体、阴天、雨天均显著提升（小目标价值扎实）；
2. **SimAM 在夜间贡献最大**（+3.7 mAP50，夜间是最难场景 baseline 仅 0.628）；
3. **SimAM + P2 组合（simam_p2）在无偏的 last.pt 指标上全面最优**；
4. **EIOU 在本任务上无显著增益**，如实报告为辅助性消融（负结果亦体现严谨性）。

### 阶段 3 要点：模型结构怎么定的

**问题**：原配置在 YAML 里直接写 `C2fSimAM`，但 ultralytics 8.3+ 的 `parse_model`
用 **`frozenset`**（`base_modules` / `repeat_modules`）判定模块是否需要自动补齐
`(c1, c2, n)` 并做宽度缩放；`C2fSimAM` 不在其中，会落入通用分支导致**通道错乱、模型无法构建**。
（曾尝试"元类 `__eq__` 别名"方案，但 `frozenset` 走哈希查找，该方案无效。）

**决策**：**SimAM 改为独立无参层**，接在每个检测头特征图（P2/P3/P4/P5）之后、`Detect` 之前。
理由：
- SimAM **不改变通道数与分辨率** → 落入 `parse_model` 通用分支（`c2 = ch[f]`）天然正确，**零 hack**；
- 与《实验设计方案》2.1 节"在每个检测头特征图之后接入 SimAM"的表述**完全一致**；
- 层索引不变（只多了末尾几个无参层），预训练权重迁移不受影响。

**验证结果**：

| 配置 | 参数量 | GFLOPs | 说明 |
|------|--------|--------|------|
| baseline (`yolov8n.yaml`) | 3,011,433 | 8.2 | 原始 YOLOv8n |
| simam (`yolov8n-simam.yaml`) | **3,011,433** | 8.2 | **与基线完全相同 → 零参数增量** |
| p2 (`yolov8n-p2.yaml`) | 2,926,956 | 12.4 | 4 检测头 |
| asp (`yolov8n-asp.yaml`) | 2,926,956 | 12.4 | SimAM+P2 |

> `C2fSimAM` 保留为"参考/可选实现"（`models/c2f_simam.py`），默认配置不使用。

### 阶段 4 要点：EIOU 补丁修了两次 bug

**Bug 1（形状广播爆炸）**
- 现象：`--eiou` 训练时 `box_loss` 达到 **1.5e4**（正常应 ~1~3）。
- 根因：ultralytics 原生 `bbox_iou` 对 `(N,4)` 输入返回 **(N,1)**，而 `eiou_loss` 返回 **(N,)**；
  在 `BboxLoss` 中 `(1.0 - iou) * weight`（weight 为 `(N,1)`）触发
  **(N,)×(N,1) → (N,N) 广播**，`.sum()` 把 N² 个元素全加起来。
- 修复：`eiou_loss` 末尾 `.unsqueeze(-1)`，输出形状与原生 `bbox_iou` 对齐。

**Bug 2（作用域过宽，污染消融语义）**
- 现象：`eiou` 变体与基线几乎无差异，且 `asp`（含 EIOU 的完整模型）反而最差。
- 根因：补丁同时替换了 `ultralytics.utils.metrics.bbox_iou`，而
  `tal.py`（`TaskAlignedAssigner`）正是从 metrics 导入并用 `CIoU=True` 计算**正样本分配指标**；
  于是"只替换回归损失"的消融被**连标签分配一起改了**，成为混淆变量。
- 修复：**只补丁 `ultralytics.utils.loss`** 模块的引用（`BboxLoss` 调用的是它），
  `metrics` 保持原生 → 分配器不变，消融只改损失一个变量。

**其他加固**：补丁幂等（避免二次包裹）；`**kwargs` 透传（兼容新版 ultralytics 对 `bbox_iou` 新增参数）。

**验证**（20000 个合法框模拟）：

```
loss.bbox_iou 已替换: True      # BboxLoss 用 EIoU
metrics.bbox_iou 未替换: True   # 标签分配器仍用原生 CIoU
tal.bbox_iou 未替换: True
模拟 loss_iou: EIoU 1.68 vs CIoU 1.47   # 量级正常
```

### 阶段 5 要点：数据链路修复清单

`scripts/convert_detrac.py`
1. **硬编码 960×540 → 读实际图像尺寸**（PIL 仅读文件头，开销极小）。
2. **`hash()` → `zlib.crc32`**：内置 `hash()` 受 `PYTHONHASHSEED` 随机化影响，
   会导致每次运行验证集划分不同、消融之间不可比。
3. **帧号错位**：XML 的 `<frame num>` 是 **1 基**（实测 `num="1"` 起），
   原代码按 `idx`（0 基）取值会整体错位一帧；
   现用 `frame_offset = min(帧号)` 自动适配 0/1 基，并修正 `--frame_interval` 抽帧时的索引。
4. **序列串扰**：`find_image_files` 原会在嵌套结构下 `rglob` 到**所有序列**的图像；
   现只取本序列目录。
5. **文件名冲突**：60 个序列都有 `img00001.jpg`，原输出会互相覆盖；
   现加序列前缀（`MVI_20011_img00001.jpg`）。
6. **官方天气标签**：从 XML 提取 `sence_weather`（官方拼写）→ 写出 `sequence_weather.csv`。

`scripts/classify_weather.py`
- 场景 key 统一为 `sunny/cloudy/night/rainy`（原来启发式产出 `day/rain`，
  与 `utils/weather_annotations.py` 的 SCENES 不一致，导致**晴天/雨天样本被静默丢弃**）；
  `normalize_scene()` 增加别名映射（`day→sunny`、`rain→rainy` 等）。
- **优先使用官方 `sence_weather`**（按序列），无官方标签时才回退亮度启发式。

`scripts/eval.py`
- 真值框还原不再硬编码 960×540，改为读实际图像尺寸（与预测框同尺度）；
- 无场景标注的图像跳过，不再默认归入 cloudy（避免污染指标）。

**路径约定统一**
- 现象：ultralytics 会把数据集 YAML 里**相对** `path` 解析到其 `datasets_dir`
  （本项目机器为 `E:\资料\基座\datasets`），而非项目根目录。
- 统一约定：数据集根 = `<datasets_dir>/ua_detrac`，`configs/ua_detrac.yaml` 写 `path: ua_detrac`；
  新增 `utils/paths.py::dataset_root()` 供各脚本统一解析。

### 阶段 6 要点：验证集必须按天气均衡划分

- 原始随机哈希划分得到的 val（8 序列）**完全没有雨天**（sunny 2 / night 2 / cloudy 4 / rainy 0），
  而"雨天/夜间提升"正是论文核心卖点 → 分场景实验会缺场景。
- 解决：以官方天气标签为依据，手工构造均衡验证集 `val_list.txt`
  （**12 个序列，四类天气各 3 个**），用 `--val_sequences val_list.txt` 重新转换。
- 最终：**train 48 序列 / 65356 图，val 12 序列 / 16645 图**，
  val 天气分布 sunny 3 / cloudy 3 / night 3 / rainy 3。

### 阶段 7 要点：GPU 与训练配置

- **环境坑**：`yolo` 环境装的是 **CPU 版 torch**（`torch 2.14.0+cpu`），
  即使有 RTX 4060 也 `cuda_available=False`；且 Python 3.14 暂无对应 CUDA wheel。
  → 新建 `yolo_gpu` 环境（Python 3.10.21 + torch 2.5.1+cu118 + ultralytics 8.4.149）。
- **batch 选择**：P2 系列模型多一个 160×160 高分辨率检测头，batch 32 时显存约 **9 GB**
  （超出 8 GB 专用显存，溢出到共享内存变慢）→ P2 类模型用 **batch 16**。
- **消融公平性**：ultralytics 默认 `nbs=64` + 梯度累积
  （`accumulate = round(nbs/batch)`），batch 16 与 32 的
  **有效 batch（64）、学习率、weight_decay、优化步数完全一致**，故混合 batch 不影响公平性。
  源码依据：`ultralytics/engine/trainer.py` 第 310~316 行。
- **断点续训**：新增 `--resume`。注意 ultralytics 的**布尔** `resume=True` 只支持
  "模型自身由 .pt 加载"的场景；本项目从 YAML 构建模型，需先把 `--resume` 解析成
  `last.pt` 的**路径字符串**（已在 `train.py` 内自动完成）。
- **随机种子**：新增 `--seed`，供多种子重复实验使用。

### 4.3 关键结论（seed=0 明细，供对照）

1. **夜间是最难场景**（baseline 仅 0.628，白天下 ~0.94），**SimAM 在这里贡献最大（+3.7）**，
   与"抑制夜间灯光干扰"的设计动机吻合。
2. **P2 增益最全面**：整体、阴天、雨天均领先，小目标检测层的价值扎实。
3. **`simam_p2` 在 last.pt 上双指标第一**（0.9128 / 0.7403）。
4. **EIOU 无显著增益**（eiou 0.9012、asp 0.9026，均接近或低于基线），
   建议在论文中如实报告为辅助性优化的负/中性结果。

### 4.5 分目标尺寸 AP（COCO 口径，n = 3）

> 面积档：small <32²、medium 32²~96²、large >96²；汇总见 `runs/eval/significance_by_size.md`。

| 变体 | AP_small | AP_medium | AP_large |

| simam | 0.3983 ± 0.0116 (+0.0097) | 0.6404 ± 0.0283 (+0.0092) | 0.8137 ± 0.0083 |

| simam_p2 | 0.3893 ± 0.0213 (+0.0007) | 0.6493 ± 0.0130 (+0.0181) | 0.8108 ± 0.0156 |
| asp | 0.3911 ± 0.0050 (+0.0025) | **0.6510 ± 0.0137** (+0.0198) | 0.8108 ± 0.0064 |

**全部 n.s.**，两条重要提醒：

1. **P2 的小目标增益不稳健**：seed=0 时 AP_small +0.0214 看着很漂亮，但三个种子分别是
   0.4189 / 0.3642 / 0.4205，方差 ±0.0321 是 baseline 的 4 倍。**不能写成"P2 显著提升小目标"**。

**结论口径建议**：论文如实写"改进在整体与分场景上呈一致正向趋势，其中阴天场景达到显著
（p<0.05），其余未达显著；EIOU 无正增益且夜间略有下降"，不要声称全面显著提升。

### 7.2 瓶颈定位与并发配置（最终结论）

单轮耗时实测（65356 张训练图，batch 32，监控子集验证）：

| 配置 | 单轮耗时 | 总吞吐（相对单进程） |
|------|---------|--------------------|
| 单进程 `workers=4` | 337 s | 0.70× |
| 单进程 `workers=7` | **237 s** | 1.00×（单进程最优） |
| 单进程 `workers=14` | 约 450 s | 0.53×（进程树膨胀到 43 个，CPU 争抢） |
| **2 进程并发 × `workers=7`** | 各自 250~283 s | **≈ 1.9×** |
| 4 进程并发（误启两份驱动时实测） | 各自 462 s | ≈ 2.0× |

**结论**：
1. GPU 不是瓶颈——单进程时利用率只有 46%，CPU 数据加载（JPEG 解码 + 增强）才是；
2. 单进程最佳 `workers=7`（容器 cgroup 配额只有 **16 核**，且宿主 load average 长期 25~37）；
3. 并发到 **2 个进程就基本吃满**（≈1.9× 总吞吐，GPU 利用率升到 73%~100%），
   再往上（4 个）总吞吐不再增长。最终采用 **`--jobs 2 --workers 7`**；
4. 单次 100 轮训练约 6.6 h、25 轮约 1.7 h，所以服务器实验把轮数压到 25 并压缩实验规模。

### 7.4.1 实测发现：25 轮对预训练模型偏长（会过拟合）

seed=0 六个运行的监控 mAP50 曲线（3000 张监控子集）：

| 变体 | ep1 | 峰值(轮次) | ep25 | 峰值→末轮 |
|------|-----|-----------|------|-----------|
| baseline | 0.9004 | 0.9057 (ep5) | 0.9009 | −0.48 |
| simam | 0.8755 | 0.9094 (ep5) | 0.8902 | **−1.92** |
| p2 | 0.9029 | 0.9157 (ep10) | 0.9031 | **−1.26** |
| eiou | 0.9007 | 0.9076 (ep10) | 0.8999 | −0.77 |
| simam_p2 | 0.8711 | 0.9106 (ep5) | 0.8899 | **−2.07** |
| asp | 0.8825 | 0.9105 (ep15) | 0.8918 | **−1.87** |

**这不是小波动，而是方向性问题**：6 个运行里有 4 个从峰值掉了 1.2~2.1 个点，
而且 `simam_p2`（峰值 0.9106）与 `baseline`（峰值 0.9057）的**排序会在末轮翻转**
（ep25：simam_p2 0.8899 < baseline 0.9009）。若只报 last.pt，会把"过拟合后的模型"
当成方法结论，甚至得出与从零训练表相反的排序。

**处理办法（已落到评估脚本）**：
1. `eval_all.sh` **同时评估 best.pt 与 last.pt**（完整 val），让数据决定报告哪个；
2. 论文口径：预训练表报 `best.pt`，并**明确交代**"best.pt 依据 val 的 3000 张分层子集选择"
   （这属于常规的验证集早停/选优，但必须写出来）；
3. `last.pt` 作为透明性对照一并给出；
4. 从零训练表仍以 last.pt 为主（那批是 100 轮 + patience=20 早停，不存在这个问题）。

### 7.4.2 实测发现：ultralytics 会自动降批（OOM 回退）

`pre_simam_p2_s0` 的命令行明明是 `--batch 32`，但日志里出现了 `batch=16`，
且训练进度条总步数是 **4085**（= 65356/16）而不是 2043（= 65356/32）。
查 `ultralytics/engine/trainer.py` 第 559~571 行确认：

```python
old_batch = self.batch_size
self.args.batch = self.batch_size = max(self.batch_size // 2, 1)
log_message = f"{error} with batch={old_batch}. Reducing to batch={self.batch_size} and retrying"
```

即 **8.4.x 在 CUDA OOM 时会自动把 batch 减半并重试（最多 3 次）**，而且只在内存里改
`args.batch`，`args.yaml` 里仍写着 32。影响评估：

- **有效批大小不变**：`nbs=64` 固定，batch 16 时 `accumulate=4`、batch 32 时 `accumulate=2`，
  优化步数与学习率调度完全一致（`weight_decay` 也按 `batch*accumulate/nbs` 归一）；
- 唯一差别是 BatchNorm 的批统计量（16 vs 32）；
- 因此该回退**不影响结论**，但必须在文档里说明；`init.txt` 记录的是**意图值**，
  真实取值要以日志里的进度条总步数为准。

### 7.4.3 判断某个 run 到底用了多大 batch

```bash
# 进度条总步数 2043 = batch32，4085 = batch16
tr '\r' '\n' < runs/seed_logs/<name>.log | grep -aoE '/[0-9]{3,5} ' | sort | uniq -c | sort -rn | head
```

### 7.4.4 显存贴顶导致的第三种环境扰动：TaskAlignedAssigner OOM 回退

3 并发时显存最高到 **24.0 / 24.5 GB**（种子 1 的重型波次：simam_p2_s1 8.1 G + p2_s1 ~5 G
+ eiou_s1 ~4 G）。此时日志里会出现：

```
WARNING ⚠️ CUDA out of memory in TaskAlignedAssigner with batch=...
```

这是 ultralytics 针对**分配器**（TaskAlignedAssigner，内存大户，尤其 P2 头的锚点数
是基线的 4 倍）的**独立回退路径**：它只让该次正样本分配走更省内存的计算，**不会**像
7.4.2 那样把训练 batch 减半，训练继续进行。

**影响与处理**：
- 属于环境性扰动（显存贴顶时的偶发），不改变 batch / 有效批大小 / 学习率调度；
- 与 7.4.2 的降批一样，是"服务器资源受限"留下的痕迹，多种子误差棒本身就包含这类噪声，
  且各变体在同一调度规则下受影响程度相当；
- 论文中无需逐条汇报，但**本工程记录与复现说明里要写明**，以便他人复现时理解
  为什么单卡并发跑会出现这两种 warning。

**发生频次的实测统计**（截至 seed=1 阶段，12 次训练 / 约 300 个 epoch）：

| run | 降批次数 | AssignerOOM 次数 |
|-----|---------|-----------------|
| pre_simam_p2_s0 | 1 | 0 |
| pre_eiou_s1 | 0 | 1 |
| pre_simam_p2_s1 | 0 | 1 |
| 其余 9 个 run | 0 | 0 |

即 **300 个 epoch 里只有 3 次孤立事件**，每次影响不超过一个 epoch 的计算路径，
对最终指标的影响可以忽略；这条统计可以直接写进论文的"实验环境与可复现性"说明。

### 7.4.6 两个评估脚本给出的是**两套不同口径**（务必别混用）

用**同一个** checkpoint（`pre_baseline_s0/weights/best.pt`）分别跑两个脚本，结果不一样：

| 脚本 | mAP50 | mAP50-95 | 口径 |

### 7.6 预训练实验结果（最终，2026-09-29 00:41 完成）

完整数据见 `docs/论文表格.md` 表 7a/7b 与 `runs/eval_server/`；以下是**结论级摘要**。

**整体指标（ultralytics 口径，n=3）**

| 口径 | baseline | 最优变体 | 最大正向差异 | 显著性 |
|------|----------|---------|-------------|--------|
| best.pt mAP50 | 0.9100 ± 0.0060 | asp 0.9126 | +0.0026 | 全 n.s. |
| best.pt mAP50-95 | 0.7393 ± 0.0036 | **p2 0.7442 ± 0.0011** | +0.0050 | 全 n.s. |
| last.pt mAP50 | 0.8889 ± 0.0083 | p2 0.8958 | +0.0069 | 全 n.s. |
| last.pt mAP50-95 | 0.7209 ± 0.0103 | **simam_p2 0.7323** | +0.0114 | 全 n.s. |

**全部显著项（仅 6 处）**：rainy mAP50-95 p2 **+0.0205\***；整体 Recall（last）p2 **+0.0403\***；
sunny mAP50（last）simam +0.0067\*；cloudy mAP50/mAP50-95（best）eiou −0.0156\*/−0.0161\*；
AP_medium（last）simam −0.0270\*。

**三条跨初始化稳健的结论**

1. **P2 检测层最稳健**：四个口径里三个第一（从零 best mAP50、预训练 best mAP50-95、预训练 last mAP50+召回）。
2. **EIOU 始终无正增益**：从零训练夜间 mAP50-95 显著 −0.0133\*，预训练阴天两指标显著 −0.0156\*/−0.0161\*。
3. **SimAM 偏向小目标**：预训练下 AP_small 0.4078（best）/0.4003（last）均高于 baseline，
   但整体不占优，且 last.pt 的 AP_medium 显著更低（−0.0270\*），是"小目标获益、中目标受损"的权衡。

**两个必须写进论文的对照发现**

- 预训练初始化把 baseline 抬高 +0.0062 mAP50，同时把 p2−baseline 从 +0.0113 压到 +0.0017、
  simam_p2−baseline 从 +0.0078 压到 −0.0002 → **更好的初始化吸收了轻量改进的增益**；
- 从零训练中"阴天显著提升（simam_p2/asp +0.0126~+0.0158\*）"在预训练下**不复现**
  （两者均 n.s.，反而是 eiou 显著为负）→ 该结论只能写成特定初始化/预算下的观察。

> **论文主结论建议**：*"P2 稳定有效；SimAM 的增益依赖初始化与场景；EIOU 无正增益"*，
> 而不是"组合模型全面最优"。
